# 复盘模板

> Step 7 用。把「复盘」从「把发生的事列出来」改成「优先找会改变下一步取舍、投入顺序、风险判断的点」。
> 与 `review-log.md`（Step 2/3/5 对抗式 Reviewer 挑刺与处置，审计）边界清晰：本文件是**提炼 + 规范反思**，不是审计流水。

## retrospective.md 格式

```markdown
# 复盘: <功能名称>

> 导向：优先找会改变下一步取舍、投入顺序、风险判断的点。
> 不是「把发生的事列出来」，是「下次遇到类似情况能做得更准/更省/更稳」。
> AGENTS.md §协作同步 已要求「复盘结论必须落到可执行改动」——本模板把该要求机械化为四题。

## 1. 影响决策的关键点（最多 3 个）
找出本任务中可能没意识到、但会显著影响后续决策的点。
每个必须包含：依据 ｜ 证据强度（强/中/弱）｜ 影响 ｜ 建议动作。
- 弱证据必须说明还缺什么信息才能升级。
- 凑不够 3 个就说「本次无第 N 个」，不硬编。

格式：
- **[点标题]**
  - 依据：<从哪观察到的——代码/日志/review 反馈/失败模式/...>
  - 证据强度：强 ｜ 中 ｜ 弱
  - 影响：<会改变什么取舍/投入顺序/风险判断>
  - 建议动作：<下一步具体做什么；弱证据写「需先 X 才能定」>

## 2. 值得封装的工作模式（最多 3 个候选项）
找出本任务中重复出现的工作模式。候选项可以是：Skill / 流程 / 模板 / 检查清单 / 脚本 / 自动化 / 文档规范 / 团队约定。
每个必须包含：触发场景 ｜ 输入 ｜ 输出 ｜ 预期收益 ｜ 误触发风险 ｜ 不应覆盖的场景 ｜ 推荐封装形式。
- 只挑跨任务会重复的；凑不够 3 个就少写。

格式：
- **[模式名称]** → 推荐封装形式：<Skill/模板/脚本/...>
  - 触发场景：<什么情况下会用到>
  - 输入：<需要什么前置信息>
  - 输出：<产出什么>
  - 预期收益：<下次能省多少时间/降低多少风险>
  - 误触发风险：<什么情况下不该用这个模式>
  - 不应覆盖的场景：<哪些任务类型不该套这个>

## 3. 项目规范的反思（最多 3 个变更候选）★ 规范轨道（强约束）
找出本任务中暴露的「规范本身的问题」——规范缺一条、规范被误读、规范与实际不符、规范该有的护栏没写明。
每个候选必须给可直接 paste 进 AGENTS.md 的条款文本。

格式：
- **[规范问题标题]**
  - 暴露事件：<本任务中哪件事暴露了这个问题>
  - 目标文件 + 章节：<AGENTS.md §协作同步 / §副作用边界 / ...；CLAUDE.md 是 symlink 自动同步>
  - 现状原文：<引用目标条款，若无则「无相关条款」>
  - 建议新增/修改条款：<可 paste 文本——格式参照 AGENTS.md §协作同步「曾因 X 导致 Y → 必须 Z」的 incident→rule 写法。**精简标尺**：一句话铁律 + 一句话事件锚定，通常 ≤ 50 字；超过 100 字大概率有同义重复，必须重构。范本：`**\`--delete-branch\` 用前必核 head**：确认 head 不是 \`dev\`/\`main\`/\`test\`，且是临时 feature 分支。曾因 PR #39 误删 dev。`（35 字）>
  - 落地状态：☐ 仅记录 ｜ ☐ 已 commit（在本任务工作分支，hash: ___）｜ ☐ 拒绝（原因：___）
  - 风险：<变更可能影响哪些既有流程>

> AGENTS.md 改动**跟着当前开发任务的 feature 分支 + PR 走**——开发任务本身就在 feature 分支 PR 进三大分支，AGENTS.md 跟代码一起 review、一起合入。不另开 docs/ PR；纯文档变更（无代码）才用 `docs/<brief>` 分支。

## 4. 结论归属标注
对第 1、2、3 题每条结论标注：
- **[本项目]**：仅基于当前项目观察，未跨项目验证
- **[推断]**：基于工程经验的一般化推断，未在多场景验证
- **[需验证]**：需更多历史记录/跨项目数据才能确认
「需验证」的东西不能直接当结论推给下次任务。
```

## 反例（什么不算合格产出）

- **题 1**：「这次踩了个 bug，下次注意」——空泛，无可执行动作
- **题 2**：「代码评审很有用」——已内建 Step 5 mini-review，不是新结论；「用了 X 库很好用」——没有触发场景/输入输出，封装不出来
- **题 3**：「应该写得更清楚」——没给现状原文 + 可 paste 条款，落不了地
- **题 3**：条款写得比 AGENTS.md 既有铁律长很多——大概率同义重复，参照 §协作同步 L72 风格精简（一句话铁律 + 一句话事件锚定）
- **通用**：凑数式填充——宁可写「本次无」也不要硬编

## 四题边界（防止重叠）

| 题 | 面向 | 产出 | 落地 |
|---|---|---|---|
| 1. 影响决策的关键点 | 下次做任务的人 | 技术/产品取舍洞察 | retrospective.md |
| 2. 值得封装的工作模式 | 流程维护者 | Skill/模板/脚本候选 | retrospective.md |
| 3. **项目规范的反思** | 规范维护者 | 规范条款变更 | **AGENTS.md 现有 §**（跟着当前任务 feature PR 走） |
| 4. 结论归属标注 | 所有读者 | 来源可信度标签 | 嵌入 1/2/3 每条 |

**判断标准**：够格立铁律 → 题 3 走 AGENTS.md 规范轨道；不够格或纯任务特定 → 留 retrospective.md。**不引入第二条沉淀轨道**（「项目记忆」类弱约束 sink 占上下文、评估成本高，砍掉）。
